# AARON 1.0 — Independent Audit (DeepSeek V4.1)

*Audit date: 2026-10-20. Target: `/home/david/proj/Aaron` (no VCS metadata present). Method: full source read of the voice, agent, tools, policy, memory and resource crates; `cargo test --workspace` re-run (656 passed, 0 failed, 0 doctests); black-box reproductions of router, wake-matcher and `listen` behaviour against the built `target/debug/aaron` with a copy of `config/` under `/tmp/opencode`. No repository file was modified except this document.*

## Verdict

**DO NOT SHIP AARON 1.0 as a voice assistant.** The text command path, tool registry, deny-by-default policy, filesystem sandbox and process hardening are substantially real and survived adversarial probing, but the voice pipeline is a demonstration harness on a fresh install: the recogniser is a fixed-phrase test double that reports itself ready, the common `espeak-ng` path produces no audible output while the preferred `piper` path always errors, and the wake matcher fires on ordinary sentences. The release also overstates its measurements, its privacy guarantees and several voice behaviours, so those claims must be corrected before AARON is described as hearing, speaking or storing nothing implicitly.

## Missing tests

- **Fresh-install voice readiness.** Nothing asserts that `listen` refuses (or loudly warns) when `auto` falls back to `ConstrainedAsr`.
- **Constrained-ASR honesty.** No test requires `info().ready == false` (or an explicit `production = false`) for the test double.
- **Wake negative corpus.** The wake tests cover a near-miss phrase and one unrelated string (`crates/aaron-wake/src/lib.rs:256-289`) but not ordinary sentences containing "hey"/"aaron", nor word-boundary collisions.
- **Router substring collisions.** No tests for `which`/`they`/`launchpad`/`killer`/`http logs`; the existing tests use curated phrasings that avoid the bug (`crates/aaron-brain/src/heuristic.rs:290-364`).
- **Speech-to-correct-action.** No end-to-end test asserts that a given audio waveform (or transcript) dispatches the intended tool; the session tests exercise the wake/strip path, not intent accuracy.
- **TTS audibility.** No test asserts that `speak()` produces audio, that it fails when the backend cannot play, or that `auto` never selects a non-playing backend.
- **`speak()` return value.** No test covers `render_wav` returning `Ok(false)`; the current implementation discards it.
- **Capture timeout semantics.** No test distinguishes an idle source from a disconnected one, or asserts that a timeout does not truncate an utterance.
- **Capture error propagation.** No test makes the CPAL error callback fire and asserts that the error reaches the caller.
- **Stale audio across turns.** No test queues audio during a long tool call and checks what the next turn transcribes.
- **Privacy of task history.** No test asserts that file contents or recall values are absent from `task_history`.
- **Correction redaction.** No test asserts that `feedback.utterance` and the resulting memory are redacted when the input contains a secret.
- **Unicode sanitisation.** No test exercises case folding that changes byte length (`İ`, `ß`, ligatures).
- **Retention of auxiliary tables.** No test asserts that `task_history`/`feedback` obey `retention_days`/`max_entries`.
- **Low-memory release ordering.** The manager tests cover `apply`, but no test drives `enforce_resource_policy` in `LowMemory` and asserts a release.
- **`Choice` with no choices.** No validation test covers the empty-list case.
- **Process hardening for whisper.** No test asserts a timeout, process-group kill, cleared environment or output cap for the ASR child.
- **`--source` documentation.** No CLI test asserts that the documented `--source synthetic` flag exists (it does not).
- **Barge-in / wake-during-command.** No test asserts what happens to a wake phrase spoken while a tool is running.
- **Authorization test count.** `docs/security.md:146,374` says 21 authorization tests; `crates/aaron-app/tests/authorization.rs` contains 22 `#[test]` functions. The count is stale.

## Resource risks

- **Unbounded file read.** `read_file` allocates the whole file before applying the 64 KiB cap (`crates/aaron-tools/src/builtin/files.rs:224-231`); a large file inside an allowed root can exhaust memory.
- **Unbounded ASR child.** `whisper-cli` has no timeout, process group, rlimits or output cap (`crates/aaron-asr/src/whisper.rs:135-140`); a hung binary blocks the voice loop, and a noisy one grows memory.
- **Pinned TTS.** `AppContext::agent()` leases TTS for the process lifetime (`crates/aaron-app/src/context.rs:351,389-396`), so idle unloading and low-memory release cannot reclaim it.
- **ASR held for the whole session.** `listen` holds the ASR guard across all turns (`crates/aaron-app/src/commands.rs:382-383`); the model stays resident even during long silences.
- **No low-memory release.** The release branch is unreachable (`crates/aaron-app/src/context.rs:413-421`) and `listen` never calls the hook; the documented behaviour does not occur.
- **Unpruned history.** `task_history` and `feedback` grow without retention (`crates/aaron-memory/src/store.rs:767-804`), each executed turn adding up to 400 characters of tool output.
- **Bounded but lossy audio.** The capture queue is bounded and drops blocks under load (`crates/aaron-audio/src/capture.rs:278-283`); the drop counter is never surfaced, so loss is silent.
- **Stale queued audio.** Capture continues during synchronous command execution (`crates/aaron-app/src/commands.rs:401-420`), so the queue can hold audio that is later interpreted as a new command.
- **No resource policy in `ask`/`listen`.** One-shot and voice commands bypass `enforce_resource_policy`, so budgets are advisory outside `run`.

## Questions for the lead

1. Is shipping the constrained recogniser as the default fallback an intentional demo decision, or should `listen` hard-fail until a real backend is configured? If intentional, why does it report `ready: true` and why is it not a readiness problem despite `doctor` showing the detail?
2. What is the intended audible-output contract for `espeak-ng`? Was `render_wav(..., "/dev/null")` meant to be a placeholder, and is the `Ok(false)` result supposed to be an error?
3. Why does `auto` prefer `PiperTts` when its `render_wav` is a guaranteed error? Is Piper intended to be selectable only with an external player?
4. Which set of benchmark numbers is authoritative — the 0.723/0.729/0.160 figures, the 0.731/0.755/0.320 figures, or the 0.741/0.7308/0.280 figures? The release needs one consistent table.
5. Is `task_history` intended to be user-visible memory subject to retention, or an operational log? Either way, should rendered file contents and recall values be stored in it?
6. Is storing the raw correction in `feedback` deliberate so a human can review the original, and if so, how is that reconciled with "corrections are sanitised on the way in"?
7. Is barge-in out of scope for 1.0? If so, should `listen` close the microphone while a tool runs to avoid interpreting queued speech as a new command?
8. Was the `State::is_listening()` microphone indicator abandoned in favour of `source.is_live()`, and is the state machine (`WakeDetected`/`Listening`/`Transcribing`) still meant to be driven by the voice path?
9. Are `task_history` and `feedback` meant to be pruned by the configured retention policy, and should `doctor` count them?
10. Is the whisper child expected to inherit the same hardening as `proc.rs` (timeout, group kill, cleared env, capped output), or is it considered trusted because the user installed it?
